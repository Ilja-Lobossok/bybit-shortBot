# Перезапуск worker: повторная свеча и риск повторного входа

Проверка кода и offline fakes от 30.10.2026. Торговая логика не изменена.
Действующий Render Worker, его Environment и disk в этой проверке не затрагивались.

## Вывод

**Повторная обработка свечи после старта есть. Она может вызвать раннее открытие
новой позиции. Обычный повторный вход при сохранённой позиции блокируется,
но строгой гарантии однократного ордера при аварийном прерывании нет.**

| Сценарий | Поведение текущего кода |
|---|---|
| Позиция или `entry_pending` сохранена в state | `open_position()` сразу возвращается, второй order не отправляется |
| Локальной записи нет, биржа возвращает ненулевой размер позиции | Проверка `get_positions()` блокирует новый order, в том числе при второй строке hedge-mode |
| Запрос позиций завершился ошибкой | Исключение не превращается в отсутствие позиции; открытие не доходит до order |
| В watchlist сохранён stall=3 после уже обработанной свечи | Новый процесс повторно читает ту же свечу, получает stall=4 и может отправить order без новой свечи |
| Прерывание после принятия order биржей, до сохранения pending | После старта локального order ID нет. Если биржевая позиция уже видна — вход блокируется; если она ещё не отражена, полного барьера от второго order нет |

Последняя строка — условный вывод по коду и асинхронной семантике API,
а не наблюдение реального дубля или измерение задержки Bybit.

## Основания в проекте

- `bot.py: ShortBot.__init__()` устанавливает `last_bar_close=0` и
  `_last_stall_check=0` на каждом старте; эти markers не сохраняются.
- `ShortBot.run()` обрабатывает свечу, когда `current_bar != last_bar_close`.
  Поэтому свежий процесс обрабатывает текущий интервал сразу, без проверки,
  что интервал уже обработан прежним процессом. Обычное ожидание внутри того
  же процесса идёт каждые 5 секунд.
- `ShortBot.check_stall()` читает `klines[-2]` и увеличивает сохранённый stall
  без проверки timestamp ранее обработанной свечи. Двухсекундный throttle
  принадлежит памяти процесса. `updated_ts` не служит candle deduplication.
- `ShortBot.open_position()` сначала проверяет `tracker.positions`, затем баланс,
  risk и биржевые позиции. Существующие guards сохранены.
- После успешного `place_order()` создаётся provisional `entry_pending`, который
  `PositionTracker.add_position()` сохраняет до следующего запроса подтверждения.
  Это защищает штатный restart после успешного сохранения.
- Однако durable intent **до** `place_order()` отсутствует. У запроса нет
  `orderLinkId`, связывающего повтор с прежним торговым намерением. Между принятием
  order биржей/получением ответа и атомарным сохранением pending остаётся окно.
- `ShortBot.cancel_all_orders_for_symbol()` не является гарантией идемпотентности:
  ошибки отмены подавляются, финальное исполнение/отмена до следующего order не
  подтверждается. Этот механизм здесь не изменяется.
- `ShortBot.check_positions()` восстанавливает сохранённые pending orders по
  `entry_order_id`; несохранённого ID в state у него нет. Подтверждённое закрытие
  атомарно сохраняет cooldown. `update_watchlist()` учитывает cooldown; это не
  замена candle/order deduplication.

Bybit документирует асинхронность создания и отмены: acknowledgement означает
принятие запроса, а не подтверждение финального состояния. Указание уникального
`orderLinkId` поддерживается API. Это не утверждение, что добавление одного поля
само по себе решило бы восстановление после crash.
[Создание order](https://bybit-exchange.github.io/docs/v5/order/create-order),
[отмена order](https://bybit-exchange.github.io/docs/v5/order/cancel-order).

Обычный SIGTERM обрабатывается `signal_handler()` установкой `running=false`:
код не проверяет этот флаг между отправкой order и сохранением pending, поэтому
текущая обработка может закончиться штатно. Это уменьшает окно при корректном
завершении, но не гарантирует завершение при kill, crash, timeout остановки или
ошибке disk. Проверка не моделирует фактические сроки остановки Render.

## Офлайн-доказательства

`tests/test_monitoring_bot.py: RestartRiskTests` выполняет реальные `run()`,
`check_stall()`, `open_position()` и чтение/запись временного state. Только API,
таймеры и отмена order заменены fakes; sockets запрещены базовым test case.

1. Та же свеча увеличивает stall 2→3. Без restart повторный проход оставляет 3.
   Новый объект процесса с тем же state и временем увеличивает до 4 и отправляет
   ровно один **fake** order. Время свечи при этом не меняется.
2. Сохранённая confirmed или pending запись после повторного чтения state
   блокирует order до биржевого запроса.
3. При отсутствии local record видимая биржевая позиция блокирует order.

Существующие accounting regressions отдельно проверяют hedge-mode guard,
ошибку запроса позиции и восстановление pending после restart. Тесты не
воспроизводят внутренние очереди биржи и не доказывают exactly-once delivery.

## Граница этого PR

Исправление candle marker, durable pre-order intent, reconciliation неизвестных
orders и idempotency требуют отдельного изменения торговой логики и тестов.
В этом PR добавлены только описание и offline characterization tests.
Нет новых Bybit calls, изменений risk/TP/SL/retries/confirmation/state schema.

Выкладка и переключение `MONITORING_ENABLED` требуют restart; это нужно учитывать
до отдельного разрешения на production. Не делать серию перезапусков в одной
свече. Сам выбор окна не устраняет окно между order acceptance и сохранением.
