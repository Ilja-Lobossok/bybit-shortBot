# Восстановление мониторинга и недоступные контракты

Инцидент 7–8 ноября 2026: подробные события отсева кандидатов и дублирующие
их ID заняли почти весь внутренний бюджет 200 MiB. Файл SQLite сохранял
выделенные страницы после DELETE, а WAL добавлялся к его физическому размеру.
Запись прекращалась до очередного checkpoint, несмотря на свободный диск.

## Что изменено

`performance/observations.py::Mailbox` агрегирует пять массовых причин
`not_usdt`, `invalid_market`, `turnover`, `pump`, `near_high` в счётчики.
Не более пяти агрегатов дополнительно к прежней ограниченной очереди.
Поле count ограничено, символы и произвольные тексты в агрегатах не сохраняются.
Входы, решения по риску и действительные снимки стратегии остаются отдельными
наблюдениями. Торговый поток не ждёт блокировку, БД или сеть.

`Store.observe` сохраняет агрегаты один раз по ID, увеличивая прежний
`decision_count` на фактический count, без строки detail для каждого тикера.
Уже сохранённые суммы счётчиков не пересчитываются из удалённой детализации.

`Store.maintenance` ограничивает strategy_events последними 20 000 строками
и 24 часами, observations — 50 000 ID и 7 днями. Удаление порциями до 500
строк на транзакцию, общий бюджет прохода около 10s. Если старый журнал не
обработан полностью, следующий проход через минуту; в норме через 5 минут.
На длительном читателе и растущем WAL уборка откладывается. Текущее состояние
стратегии, ownership, facts, revisions, account_snapshots, extrema position_runs
и `state.json` не удаляются. Существующее ограничение position_samples сохранено.
Для удалённых ID сохраняется временной floor, чтобы старый replay не увеличил
decision_count повторно. Наблюдения старше floor больше не принимаются;
финансовая дедупликация по exchange IDs действует независимо и не истекает.

`Store.check_budget` считает занятые страницы, исключая freelist, плюс WAL/SHM.
Поэтому свободные страницы внутри старого файла можно использовать повторно.
Рабочий бюджет остаётся 200 MiB; основному файлу задан max_page_count, для
WAL предусмотрено 32 MiB дополнительного пространства. Обычные записи также
ограничены общим физическим размером и прежним резервом 200 MiB свободного
диска. Vacuum, замена или удаление существующей БД не требуются. Крупные
старые файлы не становятся автоматически маленькими: физический размер и
занятые страницы показываются раздельно. Настоящее исчерпание финансового
бюджета по-прежнему требует архивации/проверки, а не удаления денег из журнала.

При отставании общего watermark более 15 минут `Runtime` запускает прежнюю
ограниченную GET-сверку раз в минуту, после восстановления — раз в 5 минут.
Число страниц за один проход, лаг 2 минуты, rate limit 1 GET/s и обработка
ошибок Reader сохранены. Новые торговые запросы не добавлены.

## Свежесть Grafana

Новые метрики с префиксом `bot_performance_`:

- `storage_used_bytes`, `storage_budget_bytes`: занятые страницы и бюджет;
- `storage_detail_rows`, `storage_dedup_rows`: размеры необязательных таблиц;
- `closed_history_timestamp_seconds`: watermark закрытий, а не время экспорта.

Trading Dashboard получил основной статус: 0 — ошибка записи/устаревшие
снимки; 1 — снимки свежие, история догружается; 2 — свежие снимки и общий
watermark не старше 30m. Equity/wallet графики показывают данные только при
возрасте реального снимка <150s. Новые карточки закрытий требуют watermark
закрытий <30m; их полнота отдельно проверяется по выбранному периоду.
График закрытий использует старый общий watermark как fallback только для
исторических интервалов до появления новой метрики. Пропущенные старые
минутные цены не восстанавливаются догадкой.

Bot Health Dashboard и существующие alert rules не меняются/не включаются.
Новых токенов, серверов, зависимостей и обязательного Loki нет.

## Bybit 110126

`live/contract_availability.py` хранит только символ и срок недоступности.
Подтверждённый SDK status_code=110126 запрещает **новые входы** по этому
символу на 24 часа. Кэш до 256 символов сохраняется атомарно в
`DATA_DIR/contract_availability.json`, отдельно от `state.json`. Другие
ошибки, включая недостаток баланса, timeout и rate limit, не создают запрет.
После истечения срока применяется прежний путь исполнения. Это обработка
доступности контракта, не обход пользовательского соглашения.

При запуске читаются максимум последние 2 MiB собственного bot.log и
учитываются только точные строки этого бота с 110126 за последние 24 часа.
Так существующие отказы не требуют новых пробных ордеров. Соглашения не
подписываются; дополнительных Bybit GET/POST для проверки доступности нет.
Обычные SDK retry, аргументы и подтверждение ордеров, входные сигналы,
сайзинг, TP/SL, риск-правила, Telegram и сопровождение открытых позиций
сохранены. Временный запрет выдаёт ограниченную причину `agreement_required`.
Ошибка сохранения кэша не меняет результат уже отклонённого запроса;
сбой чтения локального gate сохраняет обычную обработку ответа биржи.

## Проверки и выпуск

`python scripts/check_performance.py` выполняет только офлайн-тесты.
Новые проверки: 10 суток агрегированных сканов; исчерпавшийся файл SQLite;
свободные страницы; длинный читатель; WAL/disk guard; дедуп после restart;
сохранность финансовых таблиц; gate после 110126 и restart; другие ошибки;
продолжение штатного закрытия уже открытой позиции.

До выпуска проверяется отдельная временная копия реальной БД: хэши facts,
revisions, ownership, account_snapshots, positions_current и position_runs
до/после maintenance должны совпасть. Никаких записей в live DB в этой проверке.
Перед merge/deploy — свежий атомарный backup state, SQLite online backup,
проверка свободного диска и Auto-Deploy Off. Terraform допускает только
update Trading Dashboard. Затем один ручной deploy, проверка исходного SHA,
целостности SQLite, размера живых данных, свежих снимков и успешной свечи.
Пропущенные закрытия догружаются штатными GET с дедупликацией; деньги сверяются
с независимым GET, без реальных тестовых ордеров.
